What is a Custom Mode?
⏱ 10 min
Definition

A custom mode is a specialized persona you define for BOB — controlling how it behaves, what tools it can use, and what it's allowed to do. Think of it as giving BOB a specific "job hat" to wear.

💡 Modes let you tailor BOB's identity, permissions, and behavior for any specific role or task — without changing the underlying model.
A Custom Mode Controls
  • 1
    Role & Identity — Who BOB "is" in this mode
  • 2
    Behavioral Instructions — How it should respond and what to focus on
  • 3
    Tool Permissions — What files and tools it's allowed to access
Why Use Custom Modes?
🎯 Specialization

Optimize modes for specific tasks like documentation writing, test engineering, or security reviews

🔒 Safety

Restrict commands or file access for sensitive operations and production environments

👥 Team Collaboration

Share standardized workflows and consistent behavior across your entire team

🧪 Experimentation

Test different configurations without affecting other modes or teammates

Restricting File Access with fileRegex

The edit group supports an optional fileRegex pattern to restrict which files the mode can modify.

groups:
  - read
  - - edit
    - fileRegex: ".*\\.(md|mdx)$"
      description: Markdown files only
  - skill
✅ Use fileRegex to create safe, scoped modes — for example, a docs mode that can only edit .md files and nothing else.

Example — Kubernetes Expert Mode

Steps to Create the Kubernetes Expert Mode
  1. 1
    Open BOB Settings → Modes tab → click + New Mode
  2. 2
    Set Name: ☸ Kubernetes Expert
  3. 3

  4. 4

YAML Configuration
customModes:

      Kubernetes specialist for

    whenToUse: >-
      Use this mode for Kubernetes

      commands, and cluster debugging.
    customInstructions: >-
      Always validate YAML structure.
      Prefer Helm for repeatable
      deployments. Explain commands
      before running them.
    groups:
      - read
      - edit
      - execute
      - mcp

What Are Custom Rules?
⏱ 5 min
Definition

Custom Rules in BOB are user-defined instructions that shape how BOB behaves — its coding style, conventions, tone, constraints, and workflow preferences — on a per-project or global basis.

They are stored in a .bob/rules/ directory as Markdown (.md) files and are automatically loaded into BOB's context.

💡 Rules are automatically picked up — no manual loading required. Just place .md files in the right directory and BOB reads them every session.
Workspace Directory Structure
.bob/
  rules/
    coding-style.md
  rules-agent/
    typescript.md
Directory Purpose
DirectoryPurpose
rules/General rules for all modes
rules-agent/Agent mode specific rules
rules-plan/Plan mode only
rules-ask/Ask mode only
rules-{mode}/Any custom mode by slug

Create Global Rules

Linux / macOS:

mkdir -p ~/.bob/rules
echo "# Global standards" > \
  ~/.bob/rules/coding-standards.md

Windows:

mkdir %USERPROFILE%\.bob\rules
echo # Global standards > \
  %USERPROFILE%\.bob\rules\coding-standards.md
Global Rule Paths
OSPath
Linux / macOS~/.bob/rules/
Windows%USERPROFILE%\.bob\rules\
Rule Priority Order

BOB combines rules from multiple sources in this order:

  1. 1
    Global rules — ~/.bob/rules/
  2. 2
    Workspace rules — .bob/rules/
✅ Within each level, mode-specific rules load before general rules. Workspace rules can override global rules.

Write a summary of every interaction
into the folder `internal-monologue/`.

⏱ 20 min
What is .bobignore?

Control which files BOB can access by creating a .bobignore file in your project root. It works just like .gitignore — list patterns to define BOB's operational scope.

🎯 Purpose
  • Protect sensitive information
  • Prevent accidental changes to build artifacts
  • Exclude large assets from BOB's context
  • Define BOB's operational scope in your workspace
ℹ️ BOB actively monitors the file — any changes reload automatically. The .bobignore file itself is always implicitly ignored so BOB cannot change its own access rules.
Pattern Syntax (same as .gitignore)
PatternDescription
node_modules/Ignores entire node_modules directory
*.logIgnores all files ending in .log
config/secrets.jsonIgnores a specific file
!important.logException — BOB will NOT ignore this file even if *.log exists
build/Ignores the build directory
docs/**/*.mdIgnores all Markdown files in docs/ and subdirectories
✅ Create the file at your workspace root: .bobignore — no additional configuration needed.

How BOB Tools Interact with .bobignore
⏱ 20 min
✅ Strict Enforcement (Reads & Writes)

These tools directly check .bobignore before any file operation. If a file is ignored, the operation is blocked:

ToolBehaviour
read_fileWill not read ignored files
write_fileWill not write to or create ignored files
apply_diffWill not apply diffs to ignored files
GetSymbolsOverviewWill not parse ignored files for code symbols
🔍 File Discovery & Listing
  • 1
    list_files — ignored files are omitted or marked with 🔒
  • 2
    Workspace environment details (open tabs, project structure) are filtered to exclude ignored items
⚠️ File Editing Tools (Potential Write Bypass)
⚠️ insert_content and search_and_replace — the final write operation may bypass .bobignore rules. Initial reads are blocked, but the save action does not have an explicit check.
🖥️ Command Execution

The execute_command tool checks if a command (from a predefined list like cat or grep) targets an ignored file — if so, the command is blocked.

Key Limitations & Scope
⏱ 20 min
Known Limitations
⚠️ Workspace-Centric Only

Rules apply only to files within the current BOB workspace root. Files outside this scope are not affected.

⚠️ execute_command Specificity

Protection is limited to a predefined list of file-reading commands (e.g. cat, grep). Custom scripts or uncommon utilities may not be caught.

⚠️ insert_content & search_and_replace

These tools may write to ignored files due to current limitations in their save mechanism — the write step does not check .bobignore.

⚠️ Not a Full Sandbox

.bobignore is powerful for controlling file access via BOB's tools, but it does not create a system-level sandbox.

Subagents — What They Are & How They Work
⏱ 20 min
What is a Subagent?

A subagent is an independent agent BOB can spawn to handle a focused, self-contained task. It runs in its own isolated context window, executes its work, and returns a summary back to the main conversation — without polluting it.

How Subagents Work
  1. 1
    A new independent agent is created with its own context window
  2. 2
    BOB passes it a description of the focused task
  3. 3
    You are prompted to approve the spawn before it starts
  4. 4
    The subagent executes the task using its available tools
  5. 5
    It returns a summary of findings back to BOB
  6. 6
    BOB uses that summary to continue the main conversation
ℹ️ The subagent does not share state, files, or tool results with BOB unless BOB explicitly passes them in the description.
Subagent Types
TypeDescriptionBest For
exploreRead-only, lighter modelSearching code, finding files, understanding structure
generalFull tool access, default modelAny self-contained task — reads, writes, commands
When BOB Uses Subagents

BOB uses subagents sparingly. All of these must be true:

  • ✓
    The task is clearly self-contained and only a summary is needed back
  • ✓
    It would add significant irrelevant content to the main context
  • ✓
    Cannot be done with one or two direct tool calls
⚠️ BOB does not use subagents for simple file reads, quick searches, single-tool operations, or when context is already available.

The 7 Golden Rules of Legacy Modernization Prompting
⏱ 15 min · Hands-on
1 · Always paste the full source

Never summarise the RPG code — paste it whole. The AI needs to see every dcl-s, every procedure, every edge case.

2 · Include the data file and expected output

sample-output.txt is your test oracle. Without it, you can't verify the Java is correct.

3 · Name the business rules explicitly

State: "low stock is quantity <= reorderPoint — do not change this to <". The AI may "fix" what it thinks is a bug.

4 · Ask it to explain before it codes

Use a "Phase 1" prompt first. Hidden business rules surface in the explanation, not in the generated code.

5 · Say what you do NOT want

"No React", "no authentication", "no external CSS frameworks" — AI assistants over-engineer unless you set boundaries.

6 · Migrate in layers, not all at once

Model → Service → Controller → View. Each layer is easier to review and test independently.

7 · Verify with numbers

  1. 1

If not installed, download from nodejs.org. You need v18+.

Step 4 — Add the GitHub Server Entry

If the file is empty / new:

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y",
        "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN":
          "YOUR_TOKEN_HERE"
      }
    }
  }
}

If the file already has other servers, add the github block alongside them:

{
  "mcpServers": {
    "sqlite": {
      "command": "npx",
      "args": ["-y",
        "@modelcontextprotocol/server-sqlite",
        "path/to/db"]
    },
    "github": {
      "command": "npx",
      "args": ["-y",
        "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN":
          "YOUR_TOKEN_HERE"
      }
    }
  }
}
⚠️ Replace YOUR_TOKEN_HERE with the token from Step 1.
Step 5 — Reload BOB
  1. 1
    Save the file — BOB hot-reloads MCP configs automatically when a workspace folder is open
  2. 2
    Check the MCP panel in BOB's UI to confirm github shows as ✅ connected
