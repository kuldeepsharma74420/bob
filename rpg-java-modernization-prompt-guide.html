Legacy Modernization · Team Prompt Guide

How to prompt an AI to convert
RPG IV → Java Spring Boot

INVREPORT.rpgle → Java 17 Spring Boot

5 phases · 12 ready-to-use prompts · copy, paste, and send to any AI assistant

Before you start — always attach these 3 files to your chat:
1. INVREPORT.rpgle — the full RPG source (never summarise it, paste it whole)
2. INVENTORY-DATA.txt — the fixed-width data file
3. sample-output.txt — the expected report output (your golden reference)
1
Understand the Legacy Code First
Make the AI explain before it writes a single line of Java
UNDERSTANDPlain-English explanation of the program
Copy prompt
I have a legacy RPG IV program called INVREPORT.rpgle running on IBM i (AS/400). I have pasted the full source code and the data file below. Before writing any Java code, please: 1. Explain in plain English what this program does from start to finish. 2. List every business rule it enforces (e.g. low stock detection, status classification). 3. Describe each procedure — printReportHeader, printDetailLine, checkLowStock, printSummary — and what it is responsible for. 4. Identify any edge cases or tricky logic I should watch out for during migration. [PASTE INVREPORT.rpgle HERE] [PASTE INVENTORY-DATA.txt HERE]
Why use this first: Forces the AI to understand before it codes. You will catch hidden business rules (like the <= in checkLowStock vs <) before they get silently changed.
UNDERSTANDMap the fixed-width data file layout
Copy prompt
The RPG program reads a fixed-width text file. Each record is 83 bytes long. Map every field by its exact byte position (1-based) and give me: - Field name - Start and end byte position - Data type in RPG - What the equivalent Java type should be - Any gotchas (e.g. implied decimal places, padding) Pay special attention to the unit price field — it is stored as an 8-digit integer with 2 implied decimal places (e.g. 00124999 means $1,249.99). [PASTE INVENTORY-DATA.txt HERE]
Why use this: Fixed-width parsing is the #1 source of bugs in legacy migrations. Off-by-one errors in substring positions cause silent data corruption.
2
Convert to Java — Layer by Layer
Migrate in small, verifiable pieces — not all at once
CONVERTData model — the InventoryRecord POJO
Copy prompt
Convert the RPG data structure dcl-ds InventoryRec into a Java POJO class called InventoryRecord. Rules: - Map dcl-s fields with packed(8:2) → BigDecimal - Map dcl-s fields with int(10) → int - Map dcl-s fields with ind → boolean - Map dcl-s fields with char(N) → String - Add a lineValue BigDecimal field (computed: quantity × unitPrice) - Add a lowStock boolean field (computed: quantity <= reorderPoint) - Add a statusDescription String field (computed: "Active", "Discontinued", or "Unknown") - Add standard getters and setters for every field Do NOT add any parsing logic yet — just the model class. [PASTE the dcl-s variable declarations from INVREPORT.rpgle HERE]
Why layer by layer: Getting the data model right first means every subsequent layer builds on a solid foundation. Mixing parsing + business logic + model in one prompt leads to messy, hard-to-test code.
CONVERTService layer — file parsing and business logic
Copy prompt
Create a Java Spring @Service class called InventoryService that reads INVENTORY-DATA.txt from the classpath and applies the same business logic as the RPG main loop. Requirements: 1. Read the file line by line using BufferedReader. 2. Parse each 83-byte fixed-width record using substring — use these exact positions (0-based Java): - productId: substring(0, 6) - productName: substring(6, 36) - category: substring(36, 56) - quantity: Integer.parseInt(substring(56, 62).trim()) - reorderPoint: Integer.parseInt(substring(62, 68).trim()) - unitPrice: new BigDecimal(parseInt(substring(68, 76).trim())).movePointLeft(2) - status: substring(76, 77) 3. Reproduce the RPG checkLowStock() procedure: flag as low stock when quantity <= reorderPoint. 4. Reproduce the RPG select/when block: status "A" → "Active", "D" → "Discontinued", else "Unknown". 5. Calculate lineValue = unitPrice × quantity using BigDecimal. 6. Return a List<InventoryRecord> of all parsed records. Do NOT change the business rule from <= to < — the original RPG uses <= and that must be preserved exactly.
Why be explicit about <= vs <: This one character difference changes which products get flagged. Spelling it out prevents the AI from "cleaning up" logic it perceives as a bug.
CONVERTSummary statistics — the printSummary procedure
Copy prompt
Create a Java class called InventorySummary that computes the same statistics as the RPG printSummary() procedure, given a List<InventoryRecord>. Compute these fields in the constructor: - totalProducts → records.size() - activeProducts → count where status = "A" - discontinuedProducts → totalProducts - activeProducts - lowStockAlerts → count where lowStock = true - outOfStockItems → count where quantity = 0 - totalQuantity → sum of all quantity values - totalInventoryValue → sum of all lineValue values (BigDecimal) - activeInventoryValue → sum of lineValue where status = "A" (BigDecimal) - averageUnitPrice → totalInventoryValue / totalProducts, scale 2, HALF_UP - averageQuantity → totalQuantity / totalProducts, scale 2, HALF_UP The expected values from sample-output.txt are: - Total Products: 16 - Active: 13, Discontinued: 3 - Low Stock Alerts: 10 - Out of Stock: 2 - Total Quantity: 1087 - Total Inventory Value: $75,323.13 - Active Inventory Value: $71,293.39
Why include expected values: Gives the AI concrete numbers to verify against. If its implementation produces different totals, it knows it made a mistake.
CONVERTWeb layer — Spring Boot controller and HTML view
Copy prompt
Create a Spring Boot @Controller and a Thymeleaf HTML template that display the inventory report in a browser. Controller requirements: - GET / → renders the Thymeleaf template named "report" - Passes "allRecords" (List<InventoryRecord>) and "summary" (InventorySummary) to the model - GET /api/report → returns the InventorySummary as JSON (@ResponseBody) HTML template requirements: - Show 8 KPI cards at the top: Total Products, Active, Discontinued, Low Stock, Out of Stock, Total Qty, Total Value, Active Value - Show a filter bar with buttons: All, Active, Discontinued, Low Stock, Out of Stock, and one button per category (Electronics, Furniture, Office Supplies, Hardware, Software) - Show a product table with columns: Prod ID, Product Name, Category, Qty, Reorder Point, Unit Price, Line Value, Status, Stock Level bar, Alert badge - Colour the Low Stock rows amber and Out of Stock rows red - All filtering must happen client-side using vanilla JavaScript (no page reload, no framework) - Column headers must be clickable to sort ascending/descending
Why specify "vanilla JavaScript": Without this, the AI may introduce React, Vue, or jQuery — unnecessary dependencies that complicate a simple migration.

Why write tests before reviewing the UI: Numbers can look right in a browser but be subtly wrong (rounding errors, off-by-one). Tests catch this before it reaches production.
VERIFYAsk the AI to explain differences it finds
Copy prompt

Why ask for explanations: "Fix it" produces a patch. "Explain it first" produces understanding — so your team knows what changed and why.
4
Refine and Enhance
Add features the RPG program could never have
REFINEReplace the flat file with a database
Copy prompt
Migrate the INVENTORY-DATA.txt flat file to a PostgreSQL database. Generate three things: 1. A CREATE TABLE SQL script: - Table name: inventory - Columns matching the RPG record layout (product_id, product_name, category, quantity, reorder_point, unit_price as DECIMAL(8,2), status CHAR(1)) - Add a primary key on product_id 2. A Spring Data JPA @Entity class called InventoryItem that maps to this table. 3. A Spring @Component called InventoryDataLoader that: - Runs once on application startup using @EventListener(ApplicationReadyEvent.class) - Reads INVENTORY-DATA.txt and inserts all 16 records into the database - Skips the load if the table already has rows (idempotent) Keep InventoryService working unchanged — just swap its data source from the flat file to the JPA repository.
Why ask for all three together: The table, entity, and loader are tightly coupled. Getting them separately often produces mismatches in column names or types.
REFINEAdd a REST API for external integrations
Copy prompt
The original RPG program only printed to a console. Add a REST API to the Spring Boot application so other systems can consume the inventory data. Add these endpoints to a new @RestController called InventoryApiController: - GET /api/products → returns all 16 products as a JSON array - GET /api/products/{id} → returns a single product by productId - GET /api/products?status=A → returns only Active products - GET /api/products?lowStock=true → returns only products where quantity <= reorderPoint - GET /api/summary → returns all summary statistics as JSON The JSON field names should be camelCase (e.g. productId, unitPrice, lineValue, lowStock). Include proper HTTP 404 responses when a product is not found. Do NOT add authentication — this is an internal tool.
Why specify "no authentication": Saves the AI generating Spring Security boilerplate you don't need yet. Add security in a separate, focused prompt.
5
Package and Deploy
Make it runnable anywhere, not just on your laptop
DEPLOYContainerise with Docker
Copy prompt
Write a Dockerfile for the Spring Boot inventory application using a multi-stage build. Stage 1 — Build: - Base image: eclipse-temurin:17-jdk - Copy pom.xml and src/ into /app - Run: mvn clean package -q -DskipTests Stage 2 — Runtime: - Base image: eclipse-temurin:17-jre - Copy only the JAR from Stage 1 (target/inventory-web-1.0.0.jar) - Expose port 8080 - Set ENTRYPOINT to run the JAR Also write a docker-compose.yml that: - Runs the Spring Boot app on port 8080 - Adds a restart: unless-stopped policy - Mounts no volumes (the data file is bundled in the JAR) The final image should be under 300 MB.
Why multi-stage build: A single-stage build would include the entire JDK and Maven in the final image (~600 MB). Multi-stage produces a lean runtime image (~200 MB).

The 7 Golden Rules of Legacy Modernization Prompting

1
Always paste the full source. Never summarise the RPG code — paste it whole. The AI needs to see every dcl-s, every procedure, every edge case.
2
Include the data file and expected output. sample-output.txt is your test oracle. Without it, you can't verify the Java is correct.
3
Name the business rules explicitly. State: "low stock is quantity <= reorderPoint — do not change this to <". The AI may "fix" what it thinks is a bug.
4
Ask it to explain before it codes. Use a "Phase 1" prompt first. Hidden business rules surface in the explanation, not in the generated code.
5
Say what you do NOT want. "No React", "no authentication", "no external CSS frameworks" — AI assistants over-engineer unless you set boundaries.
6
Migrate in layers, not all at once. Model → Service → Controller → View. Each layer is easier to review and test independently.
7
Verify with numbers. Run the Java output against sample-output.txt. If totals match, the migration is correct. If not, ask the AI to explain the discrepancy before fixing it.
